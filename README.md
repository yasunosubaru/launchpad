# Launchpad

macOS Launchpad 风格的 Windows 启动器。全屏纯黑、大图标、顶部搜索、滚轮/键盘/页码点翻页。

全新实现，**不基于** 任何既有项目。

## 用法

| 操作 | 方式 |
|---|---|
| 启动 | 桌面快捷方式 `Launchpad`，或开始菜单搜 "Launchpad" |
| 唤出 | `Ctrl+Alt+K` / `F9` / `Ctrl+Space` / `Ctrl+Alt+Space`（**四组都注册**，被占用的会在启动日志里打印） |
| 翻页 | 滚轮 / `←` `→` / 拖拽 / 点底部圆点 |
| 收起 | `Esc` / **左键点图标之间的空白** |
| **菜单** | **右键点空白** → 添加应用 / 重新载入图标 / 设置… / 关于 |
| **移除图标** | **右键点图标** → 从启动器移除（确认后生效） |
| 搜索 | 直接打字，支持中文、拼音首字母（`wx` → 微信）、全拼（`weixin`） |

首次启动会自动导入桌面上的 `.lnk`（用 `LAUNCHPAD_SOURCE` 环境变量指定别的目录），
目标已失效的会标 ⚠）。UWP/应用商店应用可以通过「右键空白 → 添加应用 → 应用商店 /
UWP 应用」加进来，用 `Get-StartApps` 取 AUMID，存成 `shell:AppsFolder\<AUMID>`，
能正常启动。

### 「移除」到底删了什么

**只从启动器里移除。磁盘上的 `.lnk` 一个字节都不动**，那个 .cmd / .exe 也一样。
那个 .lnk 可能同时出现在桌面和开始菜单里，删它不可逆，而且几乎肯定不是
「我不想在启动器里看到它」的意思。

被移除的条目会记进 `%APPDATA%\Launchpad\dismissed.json`（一条 uid 清单）。
**没有它的话**，用户删掉的图标会在**任何一次导入**后原样回来 ——「添加应用 →
浏览文件夹」会重扫源目录，库为空时的首次自动导入也会。不记墓碑的症状就是
「我明明删了它又出现了」，比不能删更糟。

想让它回来：删掉 `dismissed.json` 里对应的那行 uid，或直接重新添加。

## 安装与运行

```powershell
git clone https://github.com/yasunosubaru/launchpad.git
cd launchpad

python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt

python -m launchpad              # 驻留后台，等热键
python -m launchpad --show       # 直接显示
```

整个目录是 **portable** 的：配置、图标缓存、日志全在 `%APPDATA%\Launchpad`
和 `%LOCALAPPDATA%\Launchpad`，拷走就能换机器。

首次启动会自动导入桌面上的 `.lnk`。想导入别处：右键空白 →
「添加应用… → 浏览文件夹…」，或设环境变量：

```powershell
$env:LAUNCHPAD_SOURCE = 'D:\我的快捷方式'
```

界面层（`tests_dots` / `tests_blank` / `tests_stutter` / `tests_wheel`）
**必须跑实屏、且只能开一个实例**：`QTest.mouseMove()` 走
`QCursor::setPos()` + 平台层路由，多个同位置窗口并存时它解析不出
「光标下是谁」，move 事件会凭空消失（症状是 `_hover` 恒为 −1，像产品 bug）。
`QTest.mouseClick(Widget, ...)` 直接投递到控件，不受影响。

`tests_remove.py` / `tests_blank.py` 里凡是「右键会弹菜单」的地方，都用
`BlankAreaController.set_menu_exec()` 装了不阻塞的替身。原因很实在：
`QMenu.exec_()` 起的是**嵌套事件循环**，阻塞到用户点某一项为止；无头测试里
没有人会点，于是 `press(..., Qt.RightButton)` 永远不返回 —— 实测整个进程挂死。
换掉之后「右键走到了弹菜单这一步」照样验得到。

`test_ui.py` 用 `render()` 而不是 `grab()`——设了 `WA_TranslucentBackground` 的窗口上
`grab()` 返回全空图像，那是 Qt 这条路径的行为，不是渲染问题。

## 排列方式

设置窗口里可选三种排布、四种排序：

| 模式 | 密度（2560x1422） | 说明 |
|---|---|---|
| `grid` | 7×5 = 35/页，4 页 | 等间距规则网格 |
| `flow` | 7×5 = 35/页，4 页 | 纵向节拍贴内容不拉伸，整块居中（macOS Launchpad 那种） |
| `compact` | **160/页，1 页** | 图标 90px、隐藏文字，一屏看完 116 个应用 |

排序：`name`（拉丁在前、汉字按拼音）/ `name_rev` / `recent`（最近使用）/ `manual`。
页间距在三种模式下**恒等于页高**（实测都是 1422），所以翻页 offset 沿用
`-index × page_height` 就对，不需要为每种模式写一套偏移。

## 卡顿排查：三个真实的测量陷阱

这一节记录「经常性卡顿」的排查过程。三处测量方法本身是错的，
一开始把全部精力花在了不存在的问题上。

### 陷阱一：把测试自己的空闲当成了卡顿

最早统计 `on_frame` 的间隔，看到「每次翻页一次 121ms 停顿」，
查了图标、GC、预热线程、窗口激活、hover —— 全都不是。

真因是那个间隔**跨过了两次动画**：上一页动画的最后一帧 → 测试里
`pump()` 的空转 → 下一页动画的第一帧。这段里应用本来就没东西可做。

**只统计单次动画内部的间隔**之后，结论完全反过来：840 帧里
**0 帧超 33ms**，翻页从来没卡过。卡顿一直在别处。

### 陷阱二：用 on_frame 当卡顿探针

`on_frame` 只在动画里触发，量到的是「我们画一帧要多久」，
量不到「GUI 线程被占住了多久」——哪怕占住它的是操作系统。

正确的探针是一个 5ms 的 `QTimer` **心跳**：心跳断了多久 =
GUI 线程不可用多久。这与动画、翻页、绘制都无关，是唯一能直接
反映体感的指标。加上去之后立刻看到：空闲 0 阻塞，翻页 2 次，
但**唤出/收起每轮一次 ~100ms**。

### 陷阱三：以为卡顿在翻页

心跳一上去，位置就清楚了：

| 场景 | >33ms 阻塞 |
|---|---|
| 纯空闲 4 秒 | 0 |
| 翻页 40 次 | 2 |
| **唤出/收起 10 轮** | **10**（每轮一次，~100ms） |
| 完整 10 轮 | 17 |

### 真正的两个原因

**① 逐帧 `setWindowOpacity`**。全屏 2560×1600 窗口每改一次不透明度，
DWM 就得把整个表面带 alpha 重新合成一遍，而一帧只淡 1/130。

**② 每次 `showFullScreen()` 重建全屏表面**。

三组对比数据（心跳探针，「唤出→翻页→收起」每轮 >33ms 的顿挫次数）：

| 唤出策略 | 顿挫/轮 | max |
|---|---|---|
| 现状：每次重建 + 窗口不透明度淡入淡出（130ms） | 0.72 | 70.7ms |
| 改成内容遮罩淡入淡出（130ms） | 0.78 | 49.9ms |
| 只 `show()` 不重建 | 0.43 | 49.1ms |
| **常驻窗口 + 一次性设不透明度** | **0.00** | **10.0ms** |

### 最终做法

- **窗口常驻**：全屏表面只创建一次，之后靠不透明度 + 鼠标穿透切换可见性。
  `hide_me()` **不再调 `hide()`**，改为淡出后设
  `setWindowOpacity(0)` + `Qt.WA_TransparentForMouseEvents(True)`。
  少了后一项，这个透明的全屏窗口会把用户所有点击都吃掉。
- **淡入淡出改用内容遮罩**：在 `paintEvent` 里盖一层纯黑，而不是改窗口
  不透明度。视觉一样，成本低一个量级。
- **FADE_MS 130 → 80**：实测 130ms 的淡出要多付一倍顿挫，换来的只是多
  50ms 观感。

### 安全性验证（常驻窗口的风险）

常驻全屏置顶窗口最大的风险是把用户桌面点不动，必须验：

| 检查 | 结果 |
|---|---|
| 未显示时不挡鼠标 | 通过 |
| 显示时正确接收点击 | 通过 |
| 收起后完全让出鼠标（4 个采样点） | 通过 |
| 反复 10 轮后仍让开 | 通过 |
| **任务栏未被覆盖、可点击** | 通过 |
| Esc 仍能收起 | 通过 |

### 卡顿：三个测量陷阱

`tests_stutter` 用 5ms `QTimer` 当心跳 —— 用户看到的卡顿是
**GUI 线程被整段占住**，哪怕占住它的是操作系统而不是我们。
on_frame 只量「我们画一帧要多久」，量不到这个。

三个陷阱都踩过、都修了：

1. **把测试自己的 idle 当成掉帧。** 一开始统计含跨页的间隔，
   看到「每次翻页一次 121ms 停顿」就去查了一堆东西 —— 那 121ms
   是测试自己 `pump()` 的空闲。
2. **同一个坑复发一次。** 分组边界写错了：`turns.append([])` 在
   `goto()` 之前，于是「本次末帧 → 下次首帧」那段 idle 被算进同一组。
   40 次 × 22 帧 = 880 帧，实际只数出 840 个组内间隔 —— 正好少 40 个，
   而那 40 个里有一批 40~50ms。症状和陷阱 1 一模一样。
   现在按 on_frame 真正触发时才开新组，并加了帧数自检断言。
3. **拿真实屏幕的偶发长间隔去追。** 帧间隔偶尔到 34~52ms，
   但同时量 on_frame 自身耗时只有 p99 1.3ms / max 2.1ms（一帧预算 16.7ms），
   而且 5ms 心跳在慢帧期间照常触发（p99 15.6ms）—— 说明事件循环
   在正常空转，延迟来自合成器/DWM/调度器。offscreen 下 max 恒为 24ms，
   正因为它完全不做合成。所以判据用 **p99**，不是 max。

最终数字：

```
空闲          max  7.77ms，0 阻塞
完整循环×40   0.00 顿挫/轮，max  9.97ms
翻页动画 840 帧  p99 18.54ms，max 26.60ms
压力×60       max 28.58ms，0 阻塞
滚轮猛滑      一次手势 = 一页，延迟 0.3ms，0 顿挫
```

第 3 条之后又加了**归因判定**：心跳空洞若与 `on_frame` 的执行区间重叠
才算我们的问题，不重叠则归外部（操作系统/驱动/别的进程）。实测
「翻页动画内部无自有掉帧：自有慢帧 0 个，外部延迟慢帧 7 个不计」。
这把判据从「这台机器此刻很安静」改成「我们没有卡住用户」——
当时的测试机后台长期有其他负载，
背景 CPU 19~26%，绝对阈值注定偶发红。

### 性能测试里两处「测错对象」

`tests_perf` 原来有两条判据在测**不该测的东西**，都已改成测对的：

- **「二次启动 < 300ms」** 测的是进程冷启动，含 Qt 建 `QApplication`
  的一次性 ~300ms、`import pypinyin` 的 ~130ms、第一次
  `showFullScreen` 建立全屏窗口。这些在真实使用里**都发生在用户按
  第一次热键之前**，与热键体验无关。改成测用户真正等待的路径：
  进程热着时按 F9 到看见图标 —— 实测 `show_me` 0.9~4.6ms + 首帧合成
  9.1~26.6ms，**合计中位 13.8ms**。原阈值也偏松（300ms vs 实测 15ms），
  收紧到 100ms 留足余量。
- **「冷启动 < 800ms」** 后来调到 5000ms 又撤掉判据。冷启动主体是
  「把这些 exe 逐个解码成图标 + 写 PNG」，纯磁盘/CPU 密集，
  实测同一份代码 3 次连跑 6618 / 7830 / <5000ms —— 跟着机器负载浮动
  （测试机后台有持续负载）。
  阈值一路调大就能变绿，但那样断言不再表达任何东西。改为记录输出，
  保留三条**不受负载影响**的真不变量：取图标占 `window_init` 的主要部分、
  提取由 `_extract` 承担且落盘由 `_save` 承担、`Grid.rebuild` 自身要小。

`bench.py` 的 `make_window` 原来从不关上一个窗口，于是屏幕上叠着
多个**全屏置顶**窗口。后果有二：首帧绘制数翻倍（`processEvents` 会把
所有可见窗口都重画，干净进程 35/35 变成 70/35）、`show_me` 读数随调用
次数单调变高。现在建新窗前先 `close_previous_windows()`。

## 性能

### 真正的根因：Qt 的动画驱动只给 31fps

用户报「仍有一定卡顿」，我先按「单帧算得慢」去查，量了一堆数字，
结论是「已接近 Qt 下限」—— **那个结论是错的**。真去量帧节奏时才发现：

```
QTimer(0)                 93369 Hz   事件循环毫无限制
翻页动画（QAbstractAnimation）  31 Hz   帧间隔 p50 = 35.08ms
```

屏幕是 **144Hz**（一帧预算 6.94ms），而动画只跑 **31fps** ——
每一帧之间空 35ms。这跟「单帧算得慢」毫无关系：单帧 4.43ms 远小于
6.94ms 的预算，完全跑得动 144fps。

**`QAbstractAnimation` 的驱动（QUnifiedTimer）在 Windows 上与 vsync
对齐，实际帧率远低于显示器刷新率。** 这是 Qt 的行为，与我们的代码无关。

### 修法：自驱动 QTimer，按屏幕刷新率取间隔

```
驱动方式                     帧率      帧间隔 p50
  QAbstractAnimation（原来）    31 Hz     35.08 ms
  QTimer(0)               142717 Hz      0.01 ms
  QTimer(7ms = 1/144s)        144 Hz      6.98 ms
```

改造后实测：**31Hz → 157Hz，帧间隔 35.08ms → 6.55ms**（4.7 倍）。

`PageAnimator` 不再调 `super().start()`，改挂自己的
`QTimer(PreciseTimer)`，间隔取 `round(1000 / refreshRate())`
并夹在 `[TICK_MS_MIN, TICK_MS_MAX]`：
144Hz → 7ms、60Hz → 17ms、读不到刷新率 → 8ms。

QTimer 在 4.4ms 负载下仍稳定跑 142Hz（实测各间隔的触发率，
`PreciseTimer` / `CoarseTimer` / 默认类型三者几乎无差别），
所以自驱动是可靠的。

两处必须同步改，漏了就会出问题：
- `stop()` 要停掉自驱动定时器，否则它在 `mode=idle` 时一直空转
- `_tick_advance` 的异常处理与 `updateCurrentTime` 同样处理 ——
  `QTimer.timeout` 也是从 C++ 回调 Python，异常逃出去同样
  0xC0000409 杀掉整个进程

### 单帧成本（保留，作为背景）

144Hz 下每帧 6.94ms，实测分解：

| 部分 | 每帧 | 占预算 |
|---|---|---|
| 窗口级重绘（背景 blit） | 2.35ms | 34% |
| `Tile.paintEvent`（29 次/帧） | 1.54ms | 22% |
| `on_frame`（含 `_apply`） | 0.43ms | 6% |
| **合计** | **4.43ms** | **64%** |

`Tile` 的重绘**已经是理论最优**（逐帧验证：37.5 次/帧全部可见、
离屏 0、同帧重复 0）。

### 四条试过但**无效**的路（勿再尝试）

死结：窗口级重绘的脏区是 `(48,122) 2464x1465`，**正好等于 Grid 的整个
矩形**。Grid 占满全屏，tile 在它内部移动，Qt 就把父窗口的同一片区域
标脏 → 每帧重 blit 410 万像素的静态背景。实测没有任何人主动调
`update()`，纯粹是 Qt 的子控件移动行为。

| 尝试 | 结果 | 为什么 |
|---|---|---|
| **按脏区裁剪 blit** | 拿不到 | Qt 在 `paintEvent` 里**不给 QPainter 设剪裁**，`p.clipBoundingRect()` 返回 **0x0**。脏区只在 backing store 的 paint region 里 |
| **背景挪到独立控件** | 无效 | 翻页 72 帧里照样被标脏 18 次。Qt 会把子控件移动区域**下方的兄弟内容**一起标脏 |
| **`WA_OpaquePaintEvent` + `WA_NoSystemBackground`** | 无效 | 触发次数不变（18 次） |
| **背景降分辨率再拉伸** | 更慢 + 可见色带 | 见下 |

#### 降采样那条：教训是「量的东西 ≠ 花的东西」

试过把背景烘成 1/4 分辨率（640x400）再拉伸，**两个问题都致命**：

1. **反而更慢**：blit 从 0.958ms 涨到 **3.009ms**。拉伸 blit 要做
   双线性插值，比 1:1 拷贝贵得多。
2. **有色带**：内容区逐像素最大差 **15/255**、平均 5.74/255。

我最初的推理是「径向渐变只有 3 个色标，低分辨率采样差异 < 1/255」——
**这是错的**。那说的是**沿半径**平滑，而变化恰恰发生在**半径方向的高频处**
（0.55 处 alpha 从 34 掉向 0 是陡的）。

而那张「1/4 分辨率 0.021ms」的对照表也是错的：量的是 **pixmap 源的
大小**，不是实际 blit 到全屏的成本。**教训：优化前先确认「量的东西
== 花的东西」。**

### 教训

我在这里绕了一大圈，因为**一直在优化错的维度**：

1. 看到「卡」就假设是「单帧算得慢」，花了大量时间优化背景 blit 和
   tile 绘制 —— 而这两处要么是 Qt 固定成本，要么已经理论最优。
2. 真正该先问的是「**帧节奏是多少**」。这个数一句话就能测
   （`QTimer(0)` 跑一秒看触发次数），我却直到最后一轮才量。
3. 写测试时把 `frame_ticks` 的总数跨用例比较，等于把定时器抖动
   当成了回归信号 —— 判据本身错了。

**下次遇到「卡」，第一个要量的不是每帧成本，而是帧率。**
如果帧率远低于屏幕刷新率，那么单帧成本再优化也没意义。

### 关于换语言 / 换框架

用户提议「Qt 的上限不一定是别的的上限，不行就换语言」。查下来**不需要**：

| 组件 | 占比 | 换语言能改善吗 |
|---|---|---|
| 帧驱动 31→157Hz | **卡顿主因** | 不需要换，这是 Qt 内部的一个默认行为，换 `QTimer` 即可 |
| 窗口背景 blit | 2.35ms | 换 GPU 渲染（Direct2D/Direct3D）能降到 ~0.1ms，但**先把帧率修对再看**，当前不是瓶颈 |
| Tile 重绘 | 1.54ms | 已理论最优，换语言无收益 |
| on_frame | 0.43ms | 占 6%，无收益 |

帧率修好后（157Hz > 144Hz 屏幕刷新率），单帧 4.43ms 完全在预算内。
**换语言解决不了这个卡顿，因为它不是语言/工具的像素吞吐问题，
而是帧驱动频率问题。**

## 实现要点（都是踩过的坑）

### 滚轮翻页：三个叠在一起的缺陷

用户先报「用力滚轮下滑，直接就卡了」，改完报「直接卡的划不动了」。
查下来是**三个独立缺陷**，每一个单独都足以让滚轮不可用。

#### ① 滚轮落在图标上完全无效（这才是「划不动」）

Qt 5 **不把未处理的滚轮事件沿父链传播** —— 它只投递给光标下的那个控件。
`Tile` 没实现 `wheelEvent`，事件到它就被默认实现 ignore 掉了。

而 Launchpad 整屏几乎都被图标铺满。实测命中测试（`childAt`）：

```
页面正中 (1280,700) -> Tile      图标之间 (300,130) -> Tile
顶部行   (900,180)  -> Tile      底部附近 (1280,1450) -> Tile
                                                    7/7 个抽样点都是 Tile
```

也就是说**用户最常见的滚轮位置恰好是唯一失效的位置**。
`sendEvent` 直接验证：发给 `Grid` 会翻页，发给 `Tile` 纹丝不动。

修法是 `Tile.wheelEvent` 显式把事件转交父控件。

#### ② 搜索框/页码点里藏着第二套滚轮实现，且用滞后页码

`Launchpad.eventFilter` 原本自己调 `self.grid.goto(self.grid.page ± 1)`。
`_page` 要等动画**结束**才更新，所以用力下滑时 20 次滚轮全部读到同一个
旧页码，全部朝同一页冲 —— 滑一整屏只翻 1 页就停住，体感就是「卡」。
这是最早的「卡」。

修法：转交 `Grid.wheelEvent`，全应用只有一套滚轮逻辑。
顺带消除了「图标区一个方向、搜索框区另一个方向」的分裂行为。

#### ③ 绝不能按 `angleDelta` 的绝对值累加

曾经写死「攒够 120（Windows 经典 WHEEL_DELTA）翻一页」。但**一格的
`angleDelta` 因鼠标而异**，差别能到几十倍：经典滚轮 120、高精度/自由
滚轮可能只发 1~60、某些设备发 240/480。

- 按 120 累加 → 高精度轮要划十几下才翻一页，**正是「划不动」**
- 按 480 的 → 一格跳四页

所以 `angleDelta` **只看符号**，一个事件一页。
触控板的精细滚动走 `pixelDelta`（`angleDelta` 为 0），那边才用像素累积，
阈值取页高 1/4。

#### `_page_target`：意图立刻记账

1 和 3 之外的另一半。老代码 `self.goto(self._page ± 1)` 里 `_page` 是
**滞后量** —— 只在动画**结束**时才更新。滚轮密集到达时（每 8ms 一个刻度）
20 次事件读到的都是同一个旧页码，于是全部朝同一页去：滑一整屏只翻 1 页
就停住，一次 `delta=2400` 的猛滚也一样只翻一页。

加 `_page_target` 记录**用户已经要求的页**，立刻更新、不等动画；
动画结束时（`_finish_anim`）再把 `_page` 追上来。

修复后实测（从第 4 页滑到底，每 8ms 一个刻度）：

```
20 个滚轮事件 -> 一路翻到第 1 页，响应延迟 0.2ms，0 个 >33ms 顿挫
```

#### 像素分支的方向 bug（顺手抓到的）

`turns = int(accum / step)` 会继承 `accum` 的符号，于是
`goto(target - turns if pixel > 0 else target + turns)` 里**符号被算了两次**。
同一个手势方向，滚轮分支翻下一页、像素分支翻上一页 —— 「鼠标能滚、
触控板反着来」。修法：`turns = int(abs(accum) / step)`，方向只看 `pixel` 的符号。

#### 手势节流：「一划」= 一页（用户报「轻轻一划直接到底了」）

`_page_target` 立刻记账解决的是「滑一整屏只翻 1 页就卡住」。但改成
「一个滚轮事件 = 一页」之后，在高频设备上又撞上相反的问题：

```
3 个滚轮事件（间隔 16ms）-> 24 帧动画里连续滑过 3 页
一格滚轮的正常动画        -> 22 帧（弹簧 0.4s）
```

也就是说三次 `goto` 各自起一段动画、每次都继承上一段的速度，内容是
**连续滑过 3 页**，中间两页各只停留不到 1 帧 —— 肉眼只看到
「一滑到底，中间全跳过去」。

所以既不按 `angleDelta` 绝对值累加、也不一事件一页，而是**手势节流**：

```python
WHEEL_GESTURE_MS = 220      # 相邻事件间隔小于它 = 同一次手势

now = time.monotonic() * 1000.0
if now - self._wheel_last_ms > self.WHEEL_GESTURE_MS:
    self._wheel_gesture = 0          # 静默够久 -> 新手势
self._wheel_last_ms = now
d = 1 if angle > 0 else -1
if self._wheel_gesture == 0:         # 一次手势只消费一页
    self._wheel_gesture = d
    self.goto(self._page_target - d)
```

不变量：**一次滚动手势 = 一页，与设备 delta 量级、事件个数都无关。**

| 场景 | 事件 | 结果 |
|---|---|---|
| 经典滚轮滚一格 | 1 × 120 | 翻 1 页 ✓ |
| 高精度滚轮轻轻一划 | 20 × 小 delta | 合并成 1 页 ✓（不是「划十几下才翻一页」） |
| 快速连划 3 次 | 3 次，中间各停 >220ms | 翻 3 页，每页动画完整 ✓ |

回归测试 `tests_gesture.py`（24 项）守住全部三行，外加「1/3/8 个事件的
动画帧数必须完全相同」—— 帧数与事件个数无关就是力度已被节流的直接证据。

#### 页码点必须跟「目标页」而不是「动画当前位置」

用户报「地下标志跟不上页面的节奏」。实测 24 帧里：

```
dots        grid.page  target    动画页位
0           0          1         -0.00
0           0          2         -0.63
0           0          3         -1.13
0           0          3         -1.93     <- 内容已滑到第 3 页，圆点还在第 1 页
...                                    （22 帧全程如此）
0           3          3         -3.00     <- 落定瞬间才跳到 3
```

**圆点从头到尾没动过**。根因：`page_changed` 只在 `_finish_anim()` 里发，
也就是**动画结束后**。滚轮连翻 3 页时三次 `goto` 各起一段动画，
`page_changed` 只在最后一段结束时发一次 —— 中间两页根本没有发信号的机会。

修法是新增 `Grid.page_intent`（`goto()` 里目标页一变就发），并让
`window._sync_dots` 订阅它、取 `grid._page_target`。圆点跟的是
**用户已经要求的页**，语义与 `PageDots.mousePressEvent` 的乐观更新一致。

配套不变式：**权威值仍能纠正乐观值**。`_finish_anim` 在动画落定时
补发 `page_intent`，所以拖拽松手回弹之类的路径圆点也会跟回真值。
越界点击（圆点 6 个 / 网格 4 页，点第 6 个）现在**同步**纠正到 3 ——
旧行为是「先乐观跳到 5、动画结束再弹回 3」，那是一次可见的闪跳。

#### `QWheelEvent` 的参数顺序

`(pos, globalPos, pixelDelta, angleDelta, buttons, mods, phase, inverted)`
—— **pixelDelta 在 angleDelta 前面**。写反的话 `angleDelta().y()` 恒为 0，
事件掉进 pixelDelta 分支，症状和「滚轮完全没反应」一模一样。这个坑踩过两次。

回归测试在 `tests_wheel.py`（27 项），覆盖上述全部：Tile 转交、
图标区与搜索框区一致性、angleDelta 从 1 到 480 的任意量级、
20 格猛滑的每格目标递增、像素累积与防误触发、边界钳位、零滚轮事件。

### 分页与偏移

**`rebuild()` 必须显式把 `_offset` 归零**
之前写的是 `self._page = 0` 之后接 `self.goto(0, animate=False)`，看着等价，
实际是错的：`goto()` 的第一行 `if index == self._page and self._slide is None: return`
此刻条件恰好成立 → 直接早退，`_offset` 原封不动。
后果是「在第 3 页搜索」之后 page=0 而 offset 仍是 −2×页高，搜索结果全部落在
可视区上方，**界面一个图标都没有**（实测 24 条结果 0 个可见）。
这正是「只有一页/快捷方式没加」的真正成因——之前一直怀疑是数据问题，方向错了。
`_stop()` / `animator.cancel()` 必须排在最前，否则进行中的动画下一帧会把旧值写回来。

**不变量：`_offset == -_page × 当前页高`**
页高依赖 `self.height()`，窗口一 resize 就变。`relayout()` 里如果只重排 `_base`
而不重新对齐 `_offset`，「在第 3 页把窗口缩小」会把视口剪切掉一块：
实测 1920×1200 下每页应显示 35 个，实际只显示 25 个。

**`PageAnimator` 用正方向，`grid` 用负方向**
`goto_page()` 里是 `target = page * page_size`（第 N 页 = +N×页高），
而网格摆放需要 `y = base.y + offset`（第 N 页 = −N×页高）。
接线时要在**两处**取负：`_on_anim_frame()` 和 `_on_anim_finished()`。
只改一处的后果特别隐蔽——动画正常播完，末帧又把正号写回去，
图标整体下移一整页到屏幕外，且此后每次翻页都如此。

**程序性翻页必须清零初速度**
`PageAnimator` 默认继承当前速度（WWDC23 velocity preservation），
那是对的——但只适用于「拖拽松手后的回弹」。
点页码点、按方向键是**离散的定位请求**，继承后速度匹配会把时长从 320ms
拉长到 `eff_dur=640ms`，页面整整两倍时间才落位，主观感受就是「点了没反应」。
`goto_page()` 里传 `velocity=0.0`，拖拽路径 `end()` 不受影响。

**`_compute_base()` 必须幂等**
`relayout()` 会反复调它，而它自己会把 `_tiles` 重排成显示序。
直接拿 `self._tiles` 按 `source_index` 取，第二次调用就全错位。
必须保留一份与 `_entries` 同序的映射源 `_tiles_src`。

**`_tiles` 要是显示顺序，不是录入顺序**
`sort_mode` 默认按名称排序，`positions` / `source_index` 都是排序**之后**的次序。
两者错开时，任何「按下标切页」的代码（`tiles[lo:lo+per_page]` 当作第 N 页）
都会错——实测会把显示在第 1 页的图标算成「下一页泄漏」，一次冒出 6 个假阳性。

### Qt 控件生命周期

**Qt 给子控件的默认尺寸是 100×30**
`Grid` 是在 `Launchpad` 里、窗口还没 `show`/`resize` 时构造的，
那一刻 `width()` 只有 100：`(100-48)//7 - 24 = -17` → **图标尺寸是负数**，
`_icon_rect()` 随之产出退化矩形 `QRect(58, 0, -17, -17)`，
命中测试和跨页泄漏检测全被带偏。

**几何未就绪时不要建控件**
按 100px 宽的默认尺寸建出来的 Tile 全是错的图标尺寸，会白白触发一次按错误尺寸的
全量图标提取（实测 175ms），等真实布局出来还得按真尺寸再提取一遍。
`Grid._populate()` 推迟到 `relayout()`（`showEvent` 保证会走到）再建。

**`_cell()` 不能自己算**
排布已经交给 `layouts.compute_layout`，它对 `margin` 的解释和 `_margins()` 不一致
（实测 `_margins()` 推出 cell 宽 107，layouts 用 100）。
两套数字并存会让外部断言全部对不上，必须报 layouts 实际用的值。

**`show_me()` 里结果没变就不要重建**
每次唤出窗口都调 `grid.set_search()`，而热键唤出是最高频路径。
无条件重建等于每次白扔 116 个 Tile + 116 次图标缓存查找。
现在用**对象身份**比较（不是相等——dataclass 逐字段比较 116 条要 900 多次字符串比较），
实测第 2 次起 rebuild = 0，唤出耗时 85ms → 62.8ms。

### 动画

**spring 是真物理，不是三次贝塞尔近似**
RK4 + 定长子步（步长由弹簧参数决定而非 dt），这样 30fps 和 144fps 切同一种子步、
走同一条相空间轨迹。实测与解析解
`x(t)=exp(-ζωₙt)[cos(ω_d t)+(ζωₙ/ω_d)sin(ω_d t)]` 的最大偏差 **0.000000**。
半隐式欧拉在 k 大时阻尼项会数值发散——极端参数（k=1e6）下实测直接溢出成 NaN。

**`on_frame` 里抛异常会让进程猝死**
异常会跨过 Qt 的 C++ 虚函数帧，进程直接 `0xC0000409`，faulthandler 都抓不到。
动画 agent 第一版测试就是这么崩的。

**Apple 的 duration/bounce 换算**
`k=(2π/D)²`、`ζ=1-bounce`（bounce≥0）/ `ζ=1/(1+bounce)`（bounce<0）、
`c=2ζ√(km)`。注意 WWDC23 幻灯片上那行 `1-4π×bounce÷duration` 是转录错误
（代入 bounce=1 得 ζ=−24，与同一场演讲「bounce=100% 即无阻尼」直接矛盾）。
减速率 `.normal=0.998`/`.fast=0.99` 都是**每毫秒**保留因子，
τ = −1/ln(rate) ⇒ 499.5ms / 99.5ms。橡皮筋 f(x)=(x·d·c)/(d+c·x)，c=0.55。

### 空白区

**不能按控件矩形判定**
`Tile` 占满整个单元格（352×184），而图标只有 128×128 居中在里面。
按控件矩形判定等于把 **62% 的屏幕**都算成「点了图标」，
点在图标之间的缝隙毫无反应——用户报的「空白区跟图标无关」。
实测空白区占比：旧逻辑 37.8% → 新逻辑 **74.4%**。

**文字命中宽度必须横向封顶**
`Tile` 占满 352px 单元格，长名字量出来 288px（比图标还宽一倍），
相邻列的文字命中矩形直接接上，横向间隙归零——界面看着有缝，点下去全被当成点图标。

**事件必须挂在 Tile 上**
点击不冒泡，点在「控件内、图标外」那一圈只会到 `Tile`，永远到不了 `Grid`。

### 其它

**`usage_stamp` 的「没设过」有两种形态**
属性不存在（`None`）和从未使用（`0.0`）。只判 `None` 不够——
`library.Entry` 带了 `last_used=0.0` 默认值，循环会在它上面 `break`，
然后 `f > 0` 为假直接返回 `None`，永远轮不到下面那张使用时间表。
实测会让 2 项排序测试失败，而且症状离病因很远。

**UWP 的 AUMID 只能从 `Get-StartApps` 拿**
开始菜单里数百个 `.lnk`，字节扫描能捞到 AUMID 的数量是 **0**。
`Get-StartApps` 不到 1 秒就给几百条。扫 `.lnk` 根本拿不到 UWP。

**`os.startfile` / `explorer.exe` / `cmd /c start` / `ShellExecuteW` 都能拉起 UWP**
四种在真机实测全部成功（`ApplicationFrameHost` 起来即算通过）。
`Qt` 和 `SHGetFileInfoW` 对 `shell:` URI 都返回空 icon，
UWP logo 只能从 `C:\Program Files\WindowsApps` 读（大部分能取到）。

**为什么热键不用 Qt**
把 `RegisterHotKey` 绑到任何 `QWidget` 的 HWND 上，往那个 HWND `PostMessage`
一个 `WM_HOTKEY`，Qt 的 `nativeEvent()` 一次都不会被调用——试过主窗口，
试过专门建的 1x1 隐藏窗口，`GetWindowLongW` 确认样式是正常 `WS_POPUP`。
Qt 只把它自己关心的消息派发到 Python。改成独立线程跑原生
`GetMessage` 循环 + `HWND_MESSAGE` 窗口才通。

跨线程操作 QWidget 是未定义行为，所以原生线程只往队列塞函数，
由 GUI 线程的常驻 `QTimer` 取走执行。这个定时器**必须在 GUI 线程装**——
第一版在 `_ensure_pump` 里检查 `QApplication.instance()`，从原生线程调用时
返回 None，定时器静默没装上，队列只进不出，热键永远唤不出窗口。

**为什么不用 `WA_TranslucentBackground`**
设了它之后 Qt 在合成阶段会跳过整棵子树，控件 `isVisible()` 全是 `True`、
单独 `grab()` 也正常，但窗口里一个图标都不显示。而且背景本来就是纯黑，
`paintEvent` 每帧铺满，这个属性只有害无益。

**`Tile` 必须显式 `show()`**
`setParent()` 只改归属，不会让控件可见。漏掉时 `isVisible()` 仍返回 `True`
（父链可见），单独截图正常，只有窗口合成时整棵子树被跳过。

**翻页偏移是加不是减**
`_offset` 是负数（第 N 页 = −N × 页高），最终 `y = base.y + _offset`。
写成减号会让第 2 页的图标飞到 y=2900（应在 56），屏幕全空。
之前只断言 `offset == -页高`（那是对的）而没查图标实际落点，漏掉了这个符号错误。

**图标区必须完全透明**
`Grid.paintEvent` 要调 `super()`（不擦背景），`Tile` 不设
`WA_TranslucentBackground`。两者任一配错都会让图标区变成一块白板。

**分页只搬可视范围是错的**
控件移出可视区后就再也搬不回来，翻页后界面全空。116 个 `move()` 的开销
远小于这个 bug。

**Qt 截断会切碎多字节字符**
`QFontMetrics.elidedText` 可能把「运行」从多字节字符中间截断，
切出一个非法 UTF-8 字节。`theme.elide` 做了修正。

**`QPixmap.fromWinHICON` 在 PyQt5 里不存在**
调它会抛 `AttributeError`，而 `paintEvent` 里抛异常直接让进程崩
（0xC0000409）。改用 `QFileIconProvider`。注意占位图也是有效 `QIcon`，
`isNull()` 返回 `False`，所以不能用它判断提取是否成功——第一版"116 个图标
全部失败"就是这样被误报成"全部成功"的。

**失效快捷方式要保留**
目标读不出的 `.lnk`（UWP/损坏）如果直接丢弃，用户会以为程序吞了他的快捷方式。
现在保留并标 `missing`，界面上显示 ⚠。`Entry.from_dict` 的判据是
"字段存在"而非"值非空"，否则这些条目保存成功、重新加载时被静默跳过。

**删除必须先落盘、再改内存**
`Library.remove()` 里 `entries` 是**最后**才动的，而且只在 `save()` 成功之后。
反过来（先从内存剔掉、再 save）一旦 save 抛异常，磁盘上那条还在、内存里已经
没了 —— 界面上少一个图标，重启一次它又回来，中途退出则删除等于没发生。

写盘失败时墓碑也要撤掉，否则条目还在库里却再也导不进来（实测：注入
`save()` 抛 `OSError`，先改内存的写法让内存从 2 条掉到 1 条而磁盘仍是 2 条）。

**图标占位图不要靠像素猜**
MSIX/Squirrel 安装的 `.lnk` 会把 IconLocation 指向
`%APPDATA%\Microsoft\Installer\{GUID}\ProductIcon` —— 那是**安装程序的产品
图标**，不是应用图标，对单 exe 应用只是一块纯灰白渐变（真实案例「某 Squirrel 安装的单 exe 应用」：
烘出来只有 1224 字节、量化后仅 3 个灰阶，而同一个 exe 自带的图标有 34 种色彩、
60.9 KB）。

第一版想用像素判据解决，走了两次弯路：

1. 「是不是灰阶」→ **实测 114 个真实图标里 20 多个是 100% 纯灰阶**
   （Notion / OBS / Epic 都是黑白 logo），会把真图标全误杀。
2. 「实心像素占比」→ 数据上看着干净（真实图标落在 14%~43% 与 96%~100% 两档，
   占位图 54%），**但撞上了 CCS Theia 的真图标，它的实心占比也正好是 54%**。

两张不同的图可以有一模一样的统计特征 —— 拿像素猜语义是有极限的。
现在改成**按路径认**（`_is_installer_product_icon`），像素判据只当兜底。
正则分两段拼（`_DIR_GUID` + `_NAME_NO_EXT`），一整条里 `$` 的位置很容易写错，
而且写错时不报异常、只是**静默地一条都不匹配**。要求「文件名无扩展名」是为了
放过 Office / `C:\Windows\Installer` 下的真图标（本机库里有 5 条，只共享
Installer 这个词）。

**右键菜单的可发现性**
「添加应用」写在右键菜单里，但菜单**从来没被显示过** —— `show_menu()` 零调用点，
右键直接 `emit settings_requested` 打开设置窗口，于是整条 `add_requested`
链路都是死代码。表现是「添加功能我根本没找到」。

## 数据位置

| 内容 | 路径 |
|---|---|
| 应用库 | `%APPDATA%\Launchpad\shortcuts.json` |
| 已移除条目（墓碑） | `%APPDATA%\Launchpad\dismissed.json` |
| 用户设置 | `%APPDATA%\Launchpad\settings.json` |
| 图标缓存 | `%LOCALAPPDATA%\Launchpad\icons\` |
| 日志 | `%LOCALAPPDATA%\Launchpad\launchpad.log` |

写入是原子的（临时文件 + `os.replace`）。库或设置损坏时抛异常并备份成
`shortcuts.corrupt-<时间戳>.json` / `settings.corrupt-<时间戳>.json`，**原文件不删**。

`settings.json` 读取时对每个键做类型校验和范围钳制：手改坏了不会导致程序起不来，
退回默认值即可。

`dismissed.json` 是唯一的例外：读不出来时按**空集**处理、不抛异常。丢一次的
代价只是某个被删过的图标在下次导入时复活，而在这里抛异常会让整个库加载
失败、启动器直接打不开 —— 为一个可丢的缓存文件牺牲可用性，比例完全不对。

## 性能实测（2560×1600，116 个应用）

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 单帧 render p99 | 19.98ms | **0.70ms** |
| 翻页每帧 p99 | — | **0.091ms**（max 0.647ms） |
| 热键唤出（第 2 次起） | 重建 116 控件 | **rebuild = 0**，62.8ms |
| 唤出/收起顿挫 | 0.72 次/轮，max 70.7ms | **0.00 次/轮，max 9.97ms** |
| 二次启动 | 690.8ms | 350ms |

**帧率问题不在渲染**。优化前单帧 p99 就已经超了 16.7ms 的 60fps 预算，
真正的做法是把标签/底板/描边**烘成 QPixmap**（单帧快 2.8×），
而不是缓存 `QIcon.pixmap()`——后者实测单次 0.0004ms，缓存它收益≈0。

**首次启动的大头是图标提取**：`_extract` 1490ms + `_save` 653ms，
全压在首次显示的关键路径上。另外「进程内第一次 `drawText`」有 250–280ms 的
字体引擎固定代价（与字体无关，第二次只要 0.1ms），已挪到后台线程预热，
启动 874ms → 457ms。

## 已知限制

- 热键是 `RegisterHotKey`，全局独占。别人先注册你就拿不到，
  启动日志会打印哪些成功哪些失败。
- 冷启动首次显示仍要等图标提取完（~2s）；磁盘缓存命中时 ~350ms。
  要再压需要把图标提取整体挪到后台线程 + 控件先用占位图，
  但那会让首帧拿不到真图标，与 `test_ui` 的「首帧 35 个图标都画出来了」冲突。
- `compact` 模式内容顶对齐，条目不满一屏时底部会留空白。
- 不做实时背景渲染（用户明确要求纯黑）。
- 触屏双指捏合无法实现：本机 `HID\CUST000&COL03` 绑定在 Mouse 类上，
  `SM_MAXTOUCHES=0`，驱动层面就没有多点触控。
